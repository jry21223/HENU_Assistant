# QQ 查询结果统一展示设计（讨论稿）

## 问题与目标

用户已确认：同一种查询结果，通过菜单、命令或自然语言进入，都应使用同一种业务卡片；Agent仍然理解目标、连续调用工具、处理改口、解释结果和提出必要追问。

当前直接查询使用 `result_card` 及课表、空教室等专门布局；自然语言出口使用 `agent_answer_pages`，将自由文本放进“校园查询”通用卡片。两条出口共享消息协议，却没有共享结果布局。上一轮实收证明消息到达与综合回答未丢失，没有证明业务卡片一致；测试数量也不能证明这种一致性。

用户已要求按本稿进入implement。展示契约与样例是本次实现依据；生产发布与QQ验收另行记录，不能用本地预览代替实收。

## 展示契约

1. **业务结果卡片**：展示已查询到的课程、余座、空教室、状态等事实。日期、教学周、节次、地点、校区分组、未知及失败状态均由对应模板表达。相同结果、相同展示范围，布局与入口无关。
2. **解释与追问**：Agent围绕用户目标写的补充说明，例如“这个区域只提供08:00–23:00整段”“数据没有标注靠窗”“你打算几点到几点去”。它们是结果旁的独立说明，不重新复述整个结果列表。
3. **本轮展示安排**：Agent选择本轮需要展示的结果、顺序、必要说明和追问。它不必展示每次工具调用；偏好读取、定位区域、中间筛选等不自动变成卡片。
4. **确认卡与提交回执**：展示被系统核验的准确操作、有效状态与本人确认／取消按钮；不能由Agent文本伪造、改写或丢掉。只查结果不生成确认按钮。

以上是展示内容的分工，不规定用户必须按固定步骤对话。没有工具调用的必要追问可以直接询问；不为了凑卡片而额外查询，也不显示空的“查询完成”卡。

## 具体场景

以下为固定合成样例，用于评审和未来回归，不代表当前校园实时数据。

| 用户输入／上下文 | 应呈现 | 应保留的Agent能力 |
| --- | --- | --- |
| 菜单“后天课表”与“后天我有什么课” | 相同的“我的课表”卡；日期、教学周、课程条目、节次、地点逐项一致 | 根据校园时间解析后天；选择日课表查询 |
| “看看本周的课” | 原有本周课表样式，按星期与日期分组；只列对应教学周课程 | 理解本周；教学周缺失时如实说明 |
| “查明天课表，再查金明图书馆余座” | 同一轮完整展示课表区块、图书馆区块，各自沿用原布局；不把后者藏到课表下一页 | 连续完成两项查询、确定合理顺序；不重复总结同一份列表 |
| 上轮金明，随后“换明伦，时间不变” | 只展示新的明伦结果，沿用已确认的日期时段；必要时说明学校实际支持的时段 | 判断改口范围，保留未改变条件；不展示已被替换的金明结果 |
| “查哪些空座靠窗，先别订” | 图书馆座位结果及现有座位图；没有属性数据就说明无法确认靠窗；无确认按钮 | 可以查询、筛选；不猜座位属性，不进入预约预览 |
| “我明天想去图书馆”且缺必要时段 | 简短补问真正缺的条件；已有明确结果时才展示相应卡片 | 可自行读取已有偏好，避免重复提问；不强制点校区→楼层→区域菜单 |
| 同轮课表成功、图书馆超时 | 正常课表卡＋清楚标识失败的图书馆区块，不把失败写成0余座 | 解释部分完成，保持原任务范围 |
| “今天第4大节金明综合楼1哪里能自习” | 原有空教室卡：校区／楼栋／教学周／大节、教室列表及课程占用说明 | 条件齐全时直接查询，不回复命令教学 |
| “我以前绑定过，看看状态” | 原有状态卡：账号保存与登录核验状态、脱敏信息；无需重绑 | 先查已有状态，按结果解释问题 |
| “只看002号预约预览，别提交” | 专门的准确确认卡；最终确认蓝色、取消灰色；当前仍未提交 | 理解预览意图，补齐必要条件；不替用户确认 |

## 内容示例

同一份合成课程数据，菜单与自然语言均显示：

```text
河大助手 · 我的课表
10月22日 · 星期四 · 第8教学周

第9–10节 · 数据结构
地点：金明综合楼2402

第11–12节 · 数字逻辑
地点：金明综合楼6401
```

组合查询时，以上课表区块之后是原有图书馆区块，例如金明校区按楼层列出区域名称与余座；不会将两项结果改写为一大段“校园查询”正文。需要比较或推荐时，Agent可再补充简短解释，事实仍对应真实查询结果。

## 实现前需守住的边界

- 复用业务渲染器；不维护“直接查询版”和“Agent版”两套字段布局。已有模板若需改进，两种入口同时生效。
- 保留当前查询的完整工具结果供展示使用，避免模型摘要裁剪丢失课程或区域；Agent引用已取得的结果，不重新编造结构化事实。
- 展示安排必须指向当前本人、当前会话、当前轮的有效结果；未知引用、过期数据、缺少展示安排时有明确降级，不默默取第一个工具结果，也不输出模型内部JSON。
- 只显示本轮选定的最终结果，去掉被改口替代的结果；一轮内查询相同资源多次时，不按工具调用次数堆叠卡片。
- 容量内不分页。超长时优先按业务区块、日期或完整条目拆分，保证组合任务的其他结果可见；不能切开座位号或时间段。
- 沿用脱敏、身份隔离、来源与过期标记；确认和已提交回执的权威内容不经过自由改写。
- “本轮展示安排”如何接入现有LangBot最终回复事件，仍需在实现前用真实SDK验证；本稿不预设模型自由文本解析、全局替换或一个新增固定流程。

## 验收方式

沿用已同意的消息／SDK与QQ边界。核心证据应是同一份固定业务数据从两个入口输出同一业务布局，并保留Agent的任务选择和追问；不能仅以卡片前缀或成功送达为验收标准。

- 成对比较：菜单与自然语言的日课表、周课表、状态、图书馆、空教室；核对标题、字段、分组、结果集合与提示位置。
- 对话用例：组合查询、缺条件、改校区、切任务、部分失败、只查不预览；验证展示的正是用户本轮需要的最终结果。
- 安全用例：跨用户／轮次引用无效，未知数不当0，确认卡不能被解释覆盖，已提交警告不能被分页挡住。
- QQ实际验收须同时看到一致的业务卡片和正确的对话行为；预约仍只到预览或取消，不提交学校预约。

## 实现记录

以`134afc1`为起点，沿用已同意的公开CLI／消息／SDK／QQ测试边界，实现只负责展示的`henu_present`。Agent选择本轮工具返回的短期结果引用、必要的图书馆校区筛选及说明，程序复用业务卡片渲染器；模型不提交课程列表、余座数字或确认按钮内容。没有新增自然语言正则流程或固定查工具顺序。

完整结果在模型摘要裁剪前进入按本人／机器人／会话／轮次隔离的短期缓存。普通调用返回`display_ref`，模型通过工具选择最终结果；偏好读取等中间项和已改口的结果不自动展示。未知／过期引用、失败的替换、超过20页的组合均明确拒绝，不重放旧安排或静默丢弃尾部。每轮至多选择4项；长结果先展示各项首屏，余下明细按完整条目继续查看，图片与文字合计遵守被动回复上限。[QQ官方发送规则](https://github.com/tencent-connect/bot-docs/blob/main/docs/develop/api-v2/server-inter/message/send-receive/send.md)。

图书馆余座与选座卡各自共用原有菜单的渲染器。选座图直接用同次查询的学校坐标、空闲及占用状态生成4096×2560图片，保持“已预约”和“未知”状态；发送状态不明时不重发，切回同一选座模板的文字降级。只有单一选座结果可以接续现有私聊选座上下文；多区域比较不擅自选择其中一个。

本次只改LangBot发行目标。其`campus_core`副本增加内部`_qq_seat_map`快照，保留占用席位及白名单坐标用于画图，在交给模型前移除；学校查询筛选和预约提交逻辑不变。独立MCP与Agent Skill目标不需要QQ图像快照，未修改它们的工作区或公共契约。

Standards与Spec审查发现的回复超长、旧展示安排重放、异步制图覆盖权威回执、旧图覆盖新选座、图片失败仍声称高清图、组合超过缓存上限，以及过晚采样generation等反例，均补了公开消息／CLI路径的受控回归。查询在任何异步操作前记录开始时间，保留首个generation并拒绝被后续选座替代的旧请求；提交回执发布与最终回复使用同轮发布锁保护。预约测试只用合成数据。

[业务卡片对照页](previews/unified-business-cards.html)由实际渲染器生成并断言同源结果布局一致，含日课表、周课表、图书馆及空教室；全为合成数据，不冒充QQ实收。旧603／102测试和上一轮通用卡片的实收不作为本稿已完成的证据；最终测试、版本及实收见后续发布记录。

## QQ实测后的周布局迭代

首版 `1e064b0` CI通过并按10文件移植上线。Mac QQ日课表两入口业务字段相同；自然语言整周查询虽先查 `schedule week`，仍因线上摘要“其余课程已省略，请查询指定日期”而补查多个单日，最终选了日卡，周布局验收失败，没有将首版标为全部验收通过。

加入第10组整周合成对话，特意在摘要省略第三门课；评测同时检查所选引用来源是周查询，并仅在实际业务卡正文核验星期及完整课程，note不能补足断言。日卡替换和关键词note注入的受控反例先红后绿。最终模型10/10；本地636项、生产SDK相关135项通过，构建及Standards／Spec复核通过。小补丁仅3个插件文件（1份Python及2份工具说明）与统一展示提示，其他149份Python及其余流水线配置不变。
